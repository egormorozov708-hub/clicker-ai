# Отчёт по практической работе «ИИ от сбора до внедрения»

**Тема:** полный цикл разработки ИИ-решения для онлайн-игры-кликера.
**Игра:** «Кликер: Становление шкафа» (Яндекс Игры).
**Дата:** 28.10.2026.
**Итоговый проект:** `Clicker_AI`, модель `best.pt` (YOLOv8n, 4 класса).

![Полный цикл проекта](docs/pipeline.png)

---

## 1. Цель и задачи

Цель — пройти полный цикл: собрать данные, разметить их, обучить модель
детекции, встроить её в программу и автоматизировать игровой процесс.

Задачи:

1. Собрать 20–30 скриншотов игры (фактически собрано 84).
2. Разметить целевой объект в X-AnyLabeling и экспортировать в YOLO HBB.
3. Обучить модель YOLOv8.
4. Написать `app.py`, который в реальном времени находит объекты и кликает.
5. Модернизировать проект: автоматизировать сбор и разметку, научить модель
   закрывать рекламу, покупать улучшения и нажимать бонусы.
6. Опубликовать проект на GitHub и подготовить демонстрацию.

---

## 2. Сбор данных

Для сбора используется `screener.py`. Скрипт:

* ищет окно браузера по части заголовка (`--window "Кликер"`);
* снимает только область окна, а не весь экран;
* сравнивает уменьшенные копии соседних кадров и пропускает почти одинаковые
  (порог `--diff`);
* сохраняет PNG в `screenshots/` с именем по дате и времени.

Итог: **84 скриншота 1920×1080** с разными положениями персонажа, состояниями
кнопок и рекламной панелью. Для обучения отобраны все 84 кадра.

![Примеры скриншотов](docs/screens_samples.jpg)

## 3. Разметка данных

### 3.1. Ручная разметка

В X-AnyLabeling открыта папка `screenshots/`, инструментом Rectangle (`R`)
обведён персонаж, класс — `game`. Разметка экспортирована в формат **YOLO HBB**,
рядом с каждым PNG лежит одноимённый JSON. Вручную размечен **31 кадр**.

Скрипт `prepare_dataset.py` преобразует JSON в txt-файлы YOLO, делит данные
на train/val в пропорции 80/20 и создаёт `data_v2.yaml`.

### 3.2. Автоматическая разметка остальных кадров

По 31 размеченному кадру обучена предварительная односклассовая модель
`game_v1` (YOLOv8n, 60 эпох, ранняя остановка на 48-й эпохе). На 6 val-кадрах
она показала **mAP@50 = 0.995**, **mAP@50-95 = 0.760**.

Этой моделью автоматически размечены оставшиеся **53 кадра**. Скрипт
`auto_label.py` сохраняет результат в двух форматах:

* JSON X-AnyLabeling — можно открыть, проверить и поправить;
* txt YOLO — сразу пригоден для обучения.

Все автоматические рамки проверены визуально по контактному листу; ошибки
(рамка на рекламном персонаже справа) отсеивались эвристикой: центр рамки должен
попадать в игровую сцену, а не в правую рекламную колонку.

### 3.3. Разметка элементов интерфейса

Кнопки улучшений, бонусов и рекламы имеют стабильные цвета, поэтому для них
написана автоматическая разметка на OpenCV (`build_dataset.py`):

* бирюзовые кнопки в левой верхней части → `bonus`;
* бирюзовые кнопки в левой нижней части → `upgrade`;
* фиолетовая кнопка «Отключить рекламу» справа сверху → `advertising`.

Такой подход быстрее ручной разметки и не зависит от субъективной оценки
границ кнопки. Для каждой картинки сохраняются все найденные кнопки (обычно
2 бонуса, 1–2 улучшения и 1 рекламная кнопка).

### 3.4. Итоговый датасет

| Класс | id | Всего | Train | Val | Что означает |
|---|---:|---:|---:|---:|---|
| `game` | 0 | 84 | 68 | 16 | персонаж — цель основного клика |
| `upgrade` | 1 | 46 | 36 | 10 | кнопки покупки улучшений |
| `advertising` | 2 | 40 | 31 | 9 | кнопка «Отключить рекламу» |
| `bonus` | 3 | 113 | 92 | 21 | бонусные кнопки 2X / +100 |

Всего **84 изображения**, разбиение **68 train / 16 val** (80/20), конфиг
`data_final.yaml` (`nc: 4`). Структура каталогов соответствует требованию
задания: `images/train` ↔ `labels/train`, `images/val` ↔ `labels/val`.

![Разметка: game, upgrade, advertising, bonus](docs/dataset_example.jpg)

### 3.5. Аугментация

`augment.py` увеличивает train-часть датасета в 3 раза. В отличие от первой
версии, рамки пересчитываются вместе с изображением (albumentations,
`BboxParams(format="yolo")`): яркость/контраст, размытие, шум, JPEG-сжатие и
небольшой сдвиг/масштаб. Горизонтальное отражение и поворот на 90° не
используются, потому что интерфейс игры несимметричен (улучшения слева,
реклама справа).

Дополнительно в `train_final.py` включены встроенные аугментации Ultralytics
(mosaic, HSV, масштаб, сдвиг). Итоговая модель обучена на исходном датасете
`dataset_final`; `dataset_aug` — готовый материал для эксперимента с большим
датасетом.

## 4. Обучение модели

### 4.1. Параметры

| Параметр | Значение |
|---|---|
| Архитектура | YOLOv8n (Ultralytics) |
| Предобучение | `yolov8n.pt` (COCO) |
| Эпох | 60 |
| Размер входа | 640×640 |
| Batch | 16 |
| Устройство | CPU |
| Seed | 0 |
| patience | 20 |
| Датасет | `data_final.yaml`, 68 train / 16 val |

Запуск: `python train_final.py`. Результаты: `runs/detect/clicker_final/`.
Лучшие веса скопированы в корень как `best.pt`, экспортированы в `best.onnx`.

### 4.2. Метрики на отложенной выборке

| Метрика | Значение |
|---|---:|
| mAP@50 | **0.989** |
| mAP@50-95 | **0.907** |
| Precision | **0.997** |
| Recall | **0.962** |

| Класс | Precision | Recall | mAP@50 | mAP@50-95 |
|---|---:|---:|---:|---:|
| `game` | 0.994 | 1.000 | 0.995 | 0.751 |
| `upgrade` | 1.000 | 0.889 | 0.972 | 0.932 |
| `advertising` | 0.996 | 1.000 | 0.995 | 0.950 |
| `bonus` | 1.000 | 0.960 | 0.995 | 0.995 |

Практическая проверка `check_detections.py` (conf = 0.35): персонаж найден на
**16/16** кадрах, средний IoU = **0.856**, все 16 рамок прошли фильтр `app.py`.
Ошибки: FP = 1 и FN = 1 у `upgrade`; у `game`, `advertising`, `bonus` ошибок нет.

Сквозной тест `app.py`: на окне с эталонным кадром обработано 87 кадров за 8 с
(≈10.5 FPS), на каждом кадре найдены `game: 1`, `upgrade: 2`,
`advertising: 1`, `bonus: 2`. Превью работает через OpenCV, а при сборке
OpenCV без GUI — через Tkinter.

Метрики получены командой:

```powershell
python validate.py --model best.pt --data data_final.yaml
```

Графики: `docs/training/results.png`, `confusion_matrix.png`,
`BoxPR_curve.png`, примеры предсказаний `val_batch*_pred.jpg`.

### 4.3. Анализ ошибок

* Основные ошибки — на кадрах, где персонаж частично перекрыт интерфейсом или
  находится у края сцены.
* Кнопки `upgrade` и `bonus` иногда путаются, если меняется цвет/размер кнопки
  после покупки; помогает временная логика в `app.py` (разные таймеры).
* Класс `advertising` представлен только фиолетовой кнопкой; крестик закрытия
  всплывающего рекламного окна в датасете отсутствует.
* Часть кадров — почти одинаковые соседние моменты, поэтому val-метрики
  выглядят оптимистично; для честной оценки нужно разделять кадры по времени
  съёмки, а не случайно.

## 5. Интеграция: программа `app.py`

### 5.1. Алгоритм

1. Найти окно игры по части заголовка (или работать по всему экрану).
2. Сделать скриншот окна/экрана.
3. Запустить YOLOv8 и получить рамки четырёх классов.
4. Отсортировать детекции по уверенности.
5. Выбрать лучшую рамку `game`, отфильтровать слишком узкие/низкие и рамки в
   правой рекламной колонке, кликнуть по центру.
6. Раз в N секунд купить улучшение (`upgrade`) и нажать бонус (`bonus`).
7. При `--close-ads` раз в N секунд нажать `advertising`.
8. Повторить цикл; в режиме `--preview` показать окно с рамками.

### 5.2. Запуск

```powershell
python app.py --model best.pt --preview
python app.py --model best.pt --dry-run --preview --max-seconds 15
python app.py --model best.pt --crop-window --window "Кликер"
python app.py --model best.pt --close-ads
```

Параметры таймеров: `--click-interval`, `--upgrade-interval`,
`--bonus-interval`, `--ad-interval`. Отключение действий: `--no-game`,
`--no-upgrades`, `--no-bonuses`.

### 5.3. Безопасность

* `pyautogui.FAILSAFE`: мышь в левом верхнем углу останавливает бота.
* Проверка активного окна: клики выполняются, только если заголовок содержит
  название игры (защита от кликов в чужие окна).
* `--dry-run` — прогон без кликов.
* `--max-seconds` — ограничение времени.
* `F8` — пауза, `F9`/`Esc` — выход (при установленном `pynput`), `Ctrl+C` —
  выход из консоли.
* DPI-awareness на Windows, чтобы координаты скриншота и мыши совпадали при
  масштабировании 125/150 %.

## 7. Ответ на вопрос задания

> **Вопрос:** а можно ли использовать авторазметку для тестирования
> работоспособности модели перед тем, как писать код?

**Ответ:** да, но как быстрый качественный тест, а не как полноценную валидацию.

* Плюсы: не нужно писать код бота, чтобы увидеть, находит ли модель персонажа и
  кнопки на новых кадрах. X-AnyLabeling показывает рамки и уверенность, сразу
  видны грубые ошибки (рамка на рекламе, пропуск персонажа, лишние объекты).
* Ограничения: авторазметка использует **ту же модель**, поэтому её
  систематические ошибки не обнаруживаются — они просто переносятся в JSON.
  Нет ground truth, нельзя посчитать precision/recall/mAP. Кроме того, человек
  видит только те кадры, которые загрузил, а не всё распределение данных.
* Правильный порядок: авторазметка → визуальная проверка 5–10 кадров → при
  необходимости ручная правка → количественная валидация на отложенной
  выборке (`validate.py --data data_final.yaml`) → только потом код бота.

## 8. Ограничения и направления развития

1. **Мало данных.** 84 кадра — минимум для устойчивой детекции. Нужно 300–500
   кадров с разными темами, разрешениями и масштабами.
2. **Похожие кадры.** Соседние скриншоты почти одинаковы; для честных метрик
   нужен split по игровым сессиям/времени.
3. **Один масштаб интерфейса.** При зуме браузера модель может ошибаться;
   поможет аугментация масштаба и сбор кадров при разном зуме.
4. **Реклама.** Размечен только фиолетовая кнопка, а не крестик всплывающего
   окна. Для реального закрытия рекламы нужно собрать кадры с попапом и
   добавить класс `ad_close` (или отдельную модель).
5. **Скорость.** На CPU инференс YOLOv8n занимает доли секунды; для более
   высокой частоты кликов можно экспортировать в ONNX Runtime/OpenVINO или
   уменьшить `imgsz`.
6. **Хрупкость к обновлениям игры.** При смене оформления модель нужно
   дообучать на новых скриншотах.
